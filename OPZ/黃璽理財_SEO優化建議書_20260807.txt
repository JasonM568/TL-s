P0-1　修正 5 個頁面的 canonical 標籤
────────────────────────────────────────────────────────────────────────────────

【現況】
實測以下 5 頁，rel=canonical 全部寫成 https://huangxi.tw（首頁）：

    /zhi-piao-tie-xian    （支票貼現，sitemap priority 0.9）
    /zhi-piao-dai-kuan    （支票貸款，sitemap priority 0.9）
    /qi-ye-dai-kuan       （企業貸款，sitemap priority 0.9）
    /faq                  （常見問題）
    /contact              （聯絡我們）

對照組——以下頁面的 canonical 都是正確的：
    /zhi-piao-dui-xian、/fei-lv-ji-suan、/ming-ci-jie-shi、所有文章頁

【問題】
canonical 等於向 Google 宣告「這一頁的正版是首頁」。
受影響的三頁，正是唯一能承接「支票貼現」「支票貸款」「企業貸款」
商業意圖流量的頁面。目前它們的排名資格被主動讓渡給首頁，
而首頁的 title 又同時塞了三個服務詞，三個關鍵字擠在同一頁互相稀釋。

這不是全站設定錯誤，是逐頁手寫 metadata 時漏改。修起來約 1 小時。

【怎麼改】
1. 在 Next.js 各該頁的 metadata 物件中，將 alternates.canonical
   改為該頁自身的絕對網址。
2. 建議一併改成從路由自動生成 canonical，避免日後新增頁面再犯：

     export async function generateMetadata({ params }) {
       const path = `/${params.slug}`
       return { alternates: { canonical: `https://huangxi.tw${path}` } }
     }

3. 部署後於 Search Console 對三頁執行「即時網址測試」，
   確認「使用者宣告的標準網址」等於頁面自身。

【完成判準】
□ 5 頁 canonical 各自指向自己
□ Search Console 網址測試顯示標準網址 = 頁面自身

【怎麼知道它失敗了】
改正後滿 4 週，Search Console「網頁索引」報告中這三頁仍顯示為
「重複，Google 選擇的標準網址與使用者不同」——代表 Google 另有判斷
（多為服務頁內容與首頁過度雷同），此時要做的是擴充服務頁內容（見 P1-3），
而不是再調 canonical。

【領先指標】
Search Console 該三頁的「已建立索引」狀態（通常 1-2 週內翻轉）→ 其後的曝光數

Google 對缺乏可驗證身分的新站會採取更保守的排名態度。

從使用者端看更直接——一家標榜服務 1,000 家企業的公司只留手機號碼，
本身就是轉換率的殺手。你的客戶要把幾十萬到幾百萬的票交給你，

【怎麼改】
1. 建立獨立的 /about 頁面，載明：

     - 公司登記地址（與營業地址若不同須說明）

     - 成立年份
     - 營業項目登記類別
     - 團隊介紹（含真人照片）

3. 頁尾固定顯示「公司全名 ＋ 統一編號」。
4. Organization / FinancialService schema 補上：

     "taxID"         統一編號
     "foundingDate"  成立年份
     "logo"          品牌識別
     "image"         辦公室實拍
     "sameAs"        [Google 商家檔案, LINE 官方帳號, Facebook 專頁]

【完成判準】
□ /about 頁上線並進入導覽列
□ 頁尾固定顯示公司全名 + 統編
□ Organization schema 含 taxID、legalName、foundingDate

────────────────────────────────────────────────────────────────────────────────

【現況】
以品牌名搜尋未見任何商家檔案訊號；

取得成本遠低於自然搜尋排名，且轉換率最高。

4. NAP（名稱／地址／電話）與官網完全一致，含市話。
5. 填滿：營業時間、服務項目、服務範圍、簡介、問答區。
6. 建立評論邀請流程，目標首季累積 15 則以上真實評論並逐則回覆。
7. 官網頁尾與聯絡頁嵌入商家檔案連結，schema sameAs 補上。

【完成判準】
□ 商家檔案通過驗證並公開顯示
□ 照片 ≥10 張（含外觀、入口、室內）

────────────────────────────────────────────────────────────────────────────────
P1-1　sitemap.xml 改為動態生成，與 llms.txt 同源
────────────────────────────────────────────────────────────────────────────────

【現況】
    sitemap.xml  收錄 97 個 URL（含 87 篇文章）
    llms.txt     宣告 94 篇文章

比對後確認以下 7 篇 8 月新文完全不在 sitemap 中：

    /articles/hua-xian-zhi-piao          （劃線支票，2026-08-07）
    /articles/fu-ze-ren-xin-yong-dai-kuan（負責人信用，2026-08-06）
    /articles/tai-zhi-yin-hang-ben-piao  （台支／銀行本票，2026-08-05）
    /articles/gong-si-lian-zheng         （公司聯徵，2026-08-04）
    /articles/zhi-piao-xie-cuo           （支票寫錯，2026-08-03）
    /articles/qing-chuang-dai-kuan       （青創貸款，2026-08-02）
    /articles/zhi-piao-ti-shi-qi-xian    （提示期限，2026-08-01）

另外，sitemap 中所有主要頁面的 lastmod 都是同一個時間戳：
    2026-07-31T04:04:22.112Z
顯示 sitemap 是建置時寫死的靜態檔，而非依內容自動生成。

【問題】
新站沒有外部連結，sitemap 幾乎是 Google 發現新頁的唯一途徑。
而這 7 篇偏偏是全站品質最高的一批（單篇約 4,000 字元，
明顯優於早期文章的 1,700 字元），卻恰好是發現不到的一批。

lastmod 全部相同也會讓 Google 逐漸降低對這份 sitemap 時間訊號的信任。

再者，llms.txt 說 94 篇、sitemap 說 87 篇——兩份「站點自述檔案」
對「本站有哪些內容」給出不同答案，這會削弱兩者的可信度。

【怎麼改】
1. 改用 Next.js 的動態 sitemap（app/sitemap.ts），
   從文章資料來源自動產生，lastmod 取各篇真實更新時間。
2. llms.txt 使用同一份資料來源生成，兩者永遠同步。
3. 加一條部署前自動檢核：sitemap 文章數 == llms.txt 文章數，
   不一致就中止部署。
4. 修正後在 Search Console 重新提交 sitemap。

【完成判準】
□ sitemap 文章數 = llms.txt 文章數 = 實際已發布文章數
□ lastmod 反映各頁真實更新時間，非同一時間戳
□ Search Console 已重新提交並顯示新的已發現網址數

【怎麼知道它失敗了】
重新提交後 2 週，Search Console sitemap 報告的「已發現網址」
仍停在 97，或這 7 篇仍未進入索引——代表問題不在 sitemap
而在內容或內部連結。

【領先指標】
Search Console sitemap 已發現網址數、新文章的首次索引天數

P1-2　www 子網域設 301 重導
────────────────────────────────────────────────────────────────────────────────

【現況】
    https://www.huangxi.tw/   → 回傳 200，內容與主網域完全相同，未重導

所幸該版本的 canonical 正確指向非 www 版本，暫時擋住了大部分風險。

【問題】
同一份內容存在兩個可存取網址，外部連結與品牌提及可能分散到兩個網域。
canonical 只是「建議」而非強制，Google 仍有機會兩版都索引。

【怎麼改】
在 Cloudflare 設一條 Redirect Rule（或 Vercel 的 redirects 設定）：
    www.huangxi.tw/*  →  301  →  huangxi.tw/$1

【完成判準】
□ curl -I https://www.huangxi.tw/ 回傳 301
□ Location 標頭指向 https://huangxi.tw/

【怎麼知道它失敗了】
設定後 curl 測試仍回 200——代表規則未套用到根網域或被 CDN 快取。

P1-3　三個服務頁擴充內容並置入內部連結
────────────────────────────────────────────────────────────────────────────────

【現況】純文字字元數實測
    /zhi-piao-tie-xian（支票貼現）      1,656 字元
    /fei-lv-ji-suan（費率試算）           767 字元
    /contact                              790 字元

對照同站文章：
    /articles/qing-chuang-dai-kuan      4,133 字元
    /articles/hua-xian-zhi-piao         3,967 字元

承接商業意圖的頁面，深度不到知識文章的一半。

另外，服務頁的內部連結僅 9 個，等同只有導覽列——
正文中沒有任何連往支援文章的連結。

【問題】
「支票貼現」這種商業詞的 SERP 由內容深厚的全國型平台佔據，
一頁 1,600 字元的服務頁在意圖滿足度上明顯不足。

更嚴重的是：94 篇文章累積的主題權重，無法透過正文連結導向服務頁。
內部連結結構等於斷開，內容資產和商業頁面各自孤立。

【怎麼改】
三個服務頁各擴充至 3,000 字元以上，建議補入：

  1. 費率計算實例（含具體數字，例如 100 萬 / 90 天票的實際到手金額）
  2. 必備文件清單（逐項說明為什麼要）
  3. 申請到撥款的時程表（第 1 天做什麼、第 2 天做什麼）
  4. 可辦與不可辦的情境
     ★ 明確寫出「什麼情況我們不承作」，這反而大幅增加可信度，
       也是與詐騙業者最有效的區隔訊號

這類內容的數據點明確、可被直接引用，是被 AI 與媒體引用的最短路徑。
建議每半年更新一次，形成「行情觀察」的定期系列。

第五部分：策略建議——為什麼要改變方向
================================================================================

【目前策略】
全國通用詞為主、內容量取勝。94 篇文章在一個月內上線。

【問題】
這條路在本站的條件下（新網域、零外部連結、YMYL 產業）
至少需要 12-18 個月才可能見效，而對手是內容規模與網域權重
都遠勝的全國型平台（Bznk 必可、誠橋 TRUSTBRIDGE 等）。

【建議：兩軌並行】

  主軌｜攻南台灣在地詞
      對手是內容淺薄的老當鋪網站（多為 2021 年前建置）
      可望 3-6 個月見效，且商業意圖強、成交率高
      → 對應 P0-3、P0-4、P2-3、P2-5

  副軌｜維持全國知識文章
      作為主題權威的地基與 AI 引用來源
      重點從「增量」轉為「提質」
      → 對應 P2-2、P2-4

★ 已投入的 94 篇文章不會浪費——
  它們正是讓在地頁具備主題支撐的關鍵。
  現在缺的只是把它們和商業頁面連起來（P1-3 的內部連結）。


【競品缺口分析】

  全國內容平台（Bznk 必可、誠橋 TRUSTBRIDGE）
    強：內容深度高、更新頻繁、網域權重強
    缺：無實體在地感、無在地服務頁、無面對面服務訴求

  高雄在地當鋪（太平、久大、格尚、新濠等）
    強：在地詞卡位早、有實體店面與市話
    缺：網站多為 2021 年前建置、無 schema、內容淺薄、
        無作者訊號、無 AI 可引用結構

  綜合貸款站（loannow、loanready 等）
    強：關鍵字覆蓋廣
    缺：內容通用、無在地、無實體、信任訊號同樣薄弱

【結論】
本站已具備當鋪型競品沒有的技術與 Schema 優勢，
也具備全國平台沒有的在地實體。

缺的只是把這兩項優勢真的表達在網站上——在地頁與信任憑證。

這是一個結構上可贏的位置，前提是先把 P0 修完。
